# Doc|Pipe User Guide

Doc|Pipe is a Java-based CLI tool designed to automate documentation generation using Large Language Models (LLMs). It allows developers to define documentation tasks ("stereotypes"), map them to specific LLM providers (Ollama, Gemini, OpenAI), and use Handlebars-based templates to generate content. It features a built-in hashing mechanism to prevent redundant API calls and supports Groovy scripting for complex prompt logic.

## Prerequisites & Setup

### Requirements
* **Java 17** or higher.
* **API Keys**: Required for cloud providers (Gemini, OpenAI).
* **Local LLM**: Ollama or LM Studio if running models locally.

### Environment Configuration
Doc|Pipe automatically loads variables from a `.env` file in the working directory. You can also provide these as System properties.

```properties
# .env file
chat.gemini.apikey=your_gemini_key
chat.openapi.api-key=your_openai_key
prjxp.docpipe.maxthreads=5
```

## Quick Start

Doc|Pipe operates on a directory-based configuration. It scans for a `.dp` folder containing the necessary instructions.

1. **Create the configuration directory**:
   Create a folder named `.dp` in your project root.

2. **Define your models (`.dp/models.json`)**:
   Map "stereotypes" to specific LLM configurations.

   ```json
   [
     {
       "stereotype": "documentation",
       "modelName": "gemma4:31b-cloud",
       "modelProviderURL": "http://localhost:11434",
       "serverType": "ollama"
     },
     {
       "stereotype": "detailed",
       "serverType": "gemini",
       "modelName": "gemini-1.5-flash",
       "timeOutSeconds": 240
     }
   ]
   ```

3. **Define your documents (`.dp/documents.json`)**:
   Specify which files to generate and which prompt templates to use.

   ```json
   [
     {
       "stereotype": "detailed",
       "outputFile": "README.md",
       "prompt": "Readme.prompt.txt",
       "ps": "\n\n_Generated by Doc|Pipe_"
     }
   ]
   ```

4. **Create a prompt template (`.dp/Readme.prompt.txt`)**:
   ```text
   Create a README for this project.
   Source code context:
   {{#java-src-dump this "../src/main/java"}}{{/java-src-dump}}
   ```

5. **Run the application**:
   ```bash
   java -jar docpipe.jar --root /path/to/your/project
   ```

## Core Concepts

### Stereotypes
Stereotypes decouple the documentation intent from the specific LLM. This allows you to use a cheap, fast model for simple tasks (like Javadoc) and a more powerful model for complex tasks (like Architecture Assessments) without changing your document definitions.

### Template Resolvers
Doc|Pipe uses Handlebars for prompt generation. Several custom helpers are available:

*   **`{{#java-src-dump context "path"}}`**: Recursively scans the specified path for `.java` files and injects their content into the prompt wrapped in Markdown code blocks.
*   **`{{#groovy}} ... {{/groovy}}`**: Executes Groovy code within the template. The script has access to the `applicationContext`, the current `dir`, and Handlebars `options`.
*   **`{{#URL "url"}}`**: Fetches and injects content from a URL.

### Hashing and Performance
To minimize token costs and execution time, Doc|Pipe generates a hash of the resolved prompt.
*   Hashes are stored in `.dp/content-hashes.properties`.
*   If the prompt content has not changed, the LLM call is skipped.
*   The runner uses a thread pool (default 5 threads) to process multiple document generations in parallel.

### Supported Server Types
The `serverType` field in `models.json` supports:
*   `ollama`: For local Ollama instances.
*   `gemini`: For Google Gemini AI.
*   `openapi`: For OpenAI or compatible APIs.
*   `lm.studio`: For local LM Studio instances (uses OpenAI protocol).
*   `custom`: For user-defined `ChatModel` implementations.

## Advanced Usage

### Custom Chat Models
You can extend Doc|Pipe by implementing the `CustomChatModel` interface. Register your implementation as a Spring `@Component`. The `CustomChatModelSupplier` will automatically pick it up if the `serverType` is set to `custom` and `canHandle(cfg)` returns true.

```java
@Component
public class MyCustomModel implements CustomChatModel {
    @Override
    public void init(DPModelConfig cfg) { /* ... */ }
    
    @Override
    public boolean canHandle(DPModelConfig cfg) {
        return "my-special-type".equals(cfg.getKiChatImpl());
    }

    @Override
    public Response<AiMessage> generate(List<ChatMessage> messages) {
        // Custom logic
    }
}
```

### Global Models
If a project directory does not contain a `models.json`, Doc|Pipe looks for a global configuration at `${projectDir}/.dp/models.json` to provide fallback model mappings.

## Best Practices & Common Pitfalls

*   **Security**: Never hardcode API keys in `models.json`. Use the `${VAR_NAME}` syntax in your configuration or rely on the `.env` file loader.
*   **Pathing**: All paths in `documents.json` and prompt templates are relative to the `.dp` directory or the project root. Ensure your `../` segments are correct when jumping from `.dp` to `src`.
*   **Timeout Management**: For large source code dumps, LLMs may take significant time to respond. Increase `timeOutSeconds` in `models.json` (default is 60s) to prevent `SocketTimeoutException`.
*   **Prompt Iteration**: Since Doc|Pipe uses hashing, if you want to force a regeneration without changing the prompt, you must manually delete the corresponding entry in `.dp/content-hashes.properties`.
*   **Memory**: When using `java-src-dump` on very large projects, the resulting prompt might exceed the LLM's context window or the JVM's heap size. Filter your source paths narrowly.
